okay so we are developing something called the PUD system (progressive unfolding database).

the idea is as follows:

there are many roots (axioms from the initial db)

and then each root has a tree under it which define the rules which have been expanded out to.

the idea is as follows:


at any given point in time, we are monitoring the leaf nodes of the PUD.

we want to know, at all times, whether any goal of any leaf node in the PUD goes either UNIT or NULL. we want to REACTIVELY detect this, so when it happens, there is effectively some work done to signal to the people who care that the body goal is unit or null.

we want to get maximum benefit from having the unfold frontier (leaf nodes) while still not suffering from the exponential time blowup of eager inference-on-inference unfolding (where the number of inferences in the db increases each unfold, and the number of NEW INFERENCES PER UNFOLD increases proportionally to the number of inferences total (exponential)).

To get benefit from both, we do "conservative unfolding". This is where we unfold a rule over the set of shallowest nodes which cause candidacy to branch further (choice points). In other words, we do the following:

suppose we have axioms a0, a1.

we have a query q.

We do the following starting at each axiom and continuing down the tree:

at each node n, we determine if there is a "unit step" or refutation from the current node. That is, we determine if there is ONLY ONE possible branch (edge) from n that has at least 1 candidate. If so, we step down that branch eagerly. Then, we repeat the question starting from the node down that branch, call it n'. We also keep exploring until we find that at least 2 of the outgoing edges at node n have leaf candidates under them. At that point, we know that if we were to unfold the rule whos body goal was the query, we would unfold against n, however specialized it may be. So basically, we continue eagerly unit-propagating the search down until we know we have a branching point (choice point). That is when we stop propagating downward.

Note that the invariant we want to preserve is this:

"At any point in time, we maintain, for each body goal of each leaf rule, a 'candidate set', which is the set of propagated-til-choice candidates for that goal." Effectively, it means that it is the set of nodes (which will always be size <= # of axioms) which are the most-specialized candidates without choice.

Not sure what to name this concept of "most specialized candidates without choice". But I think about it as just early unit-propagating down to give our unfold the most information possible.

Similarly, it is possible during this algorithm to determine that there are actually no leaf candidates anywhere under an axiom. at which point, we refute the axiom in terms of candidacy for the query given.

We use a fully persistent array and hierarchical bind map for the PUD.

we do not actually store a whole rule at every node in the PUD. instead, we just store `added_unifications` and `added_body_goals`. The idea being that added_unifications is also how we specify the root axiom heads. There is a variable which is implicitly used by the whole DB, called var(0). which is better known as the "Head Var". The axiom nodes have as an added unification, something like: var(0) = head(X, Y) where head(X,Y) is the head of the axiom rule.

also, the axioms introduce the original rule body in added_body_goals.

each specialization of that rule (unfold output) just specifies added unifications beyond that of the parent node and all ancestor nodes, since that is all that an unfold can do (specialize the parent head and introduce more body goals). Implictly, by nature of the fact that each intermediary node stores which body goal was unfolded over to produce the children, we know that body goal is no longer considered present at the descendent nodes. So everything going into defining a rule at some node comes from the ancestor nodes and the current node's deltas effectively.

similarly, we use hierarchical bindings thru the fully persistent array data structure which supports the hierarchical bind map. Thus child nodes inherit the bindings introduced at the parent node and all ancestor nodes above.

When starting a lazy query of a body goal b, we actually do the whole query inside of the binding interval of the rule which has b in its body, this way vars employed in the query can have their actual meanings looked up during the query.

When dispatching a lazy query of b, we make a note of the frame offset of the database that we are querying into. The frame offset will be equal to the LVC (lineage var count) at the node owning b. NOTE: I do not believe I mean by that the node INTRODUCING b. Instead, lazy queries only exist in terms of the body goals of the leaf rules in the database since they are the most specialized. But anyway yes, the LVC(n) is a definition of the number of contiguous vars used in the lineage up until node n.

During the query, we keep track of what caller representatives changed at every given point in the query. When finally accepting the unfold over those candidates, we store (in the resulting expanded child nodes) added_unification entries (one for each caller rep that changed). We specifically store rep : (normalize of rep with cutoff == LVC) to partially normalize and get all contiguous remainder variables out. Then, we update the LVC at each child node to be equal to the parent's LVC + the translation map size (since there will only be one entry per new remainder var coming from the callee environment, and they will all be made contiguous w.r.t. the old LVC, meaning the new child LVC can be used as the new frame offset when we query body goals from them as well).

NOTE: the binding environment of the candidate is NOT preserved after accepting the candidate to unfold over. instead, we just compute the added_unifications while in that environment, and we normalize the rhs of the added unifications while in that environment. we also normalize the "added body goals" which came from the query, while in that environment.

An invariant:
We want, in our database, at any point in time, to have ONLY un-framed expressions (const expr*) and variable indices which are global (un-framed as well). ONLY WHEN QUERYING do we construct the framed expressions on the fly with frame offset == LVC of the caller, to then do things like unification.

I believe that each node won't store an interval. the reason is this: when querying into a node, the node will have a DIFFERENT interval as it pertains to the query, since the interval of the node will need to be within the interval of the caller (leaf node) to have the binding environment of the caller in-scope...

Note that we have only one FPA for everything since the caller's bindings must be visible during the query, thus the query's binding intervals must be INSIDE that of the caller which means that we have one FPA.

Something else to note is that we have 2 different concepts of unit propagation. One I will refer to temporarily as Unit Prop A which is when UNDER A SPECIFIC ROOT (axiom), we have only one outgoing edge that has at least one candidate for the given query. When this happens, we advance the query forward automatically. NOTE: WE DO NOT ACTUALLY APPLY THE UNFOLD YET. The second type of unit prop is when there is only one remaining axiom under which a fully advanced query has candidates. In this case (Unit Prop B), we ACTUALLY CAN AFFORD to apply the unfold automatically, since it will not cause the database to grow in number of leaf rules. Perhaps we call "Unit Prop A" "Query Advancing" and B "Unit Propagation".

We want to consider what happens with the queries attached to the body goals of a rule r when r is unfolded into child rules. Sometimes, the query does not change whatsoever if the vars in the goal are not affected at all by the unfold... other times they are... I mean we have a few options, one is to take all body goals of the unfolded rule and throw away their queries, and restart at the unfolded binding contexts (child nodes' body goals). Another is to try to keep the original body goals queries going but somehow "fork" them? not sure how that would work. An adjacent thing to note is that, when starting a query for the body goals of the children, our fully advanced query from our original rule's body goals can serve as the starting point for the offspring's queries since advancing a query generally only happens when all but one outgoing edge in the search is refuted. And we know that no matter how many bindings we ADD, it can never cause things which failed to unify in the past to NOW UNIFY. In other words, if it was refuted in the past (causing us to advance our query with less specialized body goal), we can be confident that starting our query for the child rule's body goal at that same advanced position should be sufficient as well. We also know that all rules that we tried to match as candidates that failed to match for the old body goal will still fail, so maybe we can do something where our offspring's query can be some sort of a continuation of the original body goal's query.

Another thing to note is: due to the mechanism where we advance a query until a choice point, we pretty much know that under any axiom, we will only ever have at most one node which is the current "unfold candidate" and is the only candidate in the fully advanced query. This means that a single query may have at any point in time at most n candidates where n is the number of axioms in the database. To think about how the chain reaction will work, it is useful to think about what the catalysts are (what the initial changes are to the DB that could cause certain things to occur):

Rule Unfolding is our only real action at the outermost level. Any time that a rule unfolds in our database, and that rule served as a leaf witness for any candidates, we must revisit those candidates' queries, and recognize that since that witness is NO LONGER A LEAF, we must eagerly propagate the witness search downward to the new children of the old witness, until we find a replacement leaf witness. I think of this as though we are doing effectively a depth-first search for a leaf witness, and if any CURRENT LEAF WITNESS is unfolded, it is NO LONGER A LEAF. Therefore we revisit it, and RESUME depth-first search from that point. NOTE: depth-first search should follow a deterministic traversal order, so as to make it obvious what parts of the database have already been explored and ruled out in terms of witnesshood. Also note: we do NOT HAVE TO reach the leaves to refute witnesshood. This is because, when traversing down the tree (deeper), it just specializes the heads of rules MORE. This means that if any intermediary node's head could not unify with our query, that all of the heads BENEATH IT also will not be able to. 

NOTE: when unfolding a rule r and it causes it to simply refute (disappear), this is one way that a leaf witness could become a refuted witness, but actually it is NOT the only way. We could unfold r into, let's just say a few children, but EACH CHILD instantiates a variable in the head of r such that our original query which used r as a leaf witness, when resuming unto the children, may realize that whatever instantiated functors were in the query may not line up with the heads of the new child leaves, which could also refute witnesshood of all children under r.

Another note: When witnesshood gets violated by the witness unfolidng AND when continuing the DFS for a leaf witness down from it, and none of its children are viable, we have a situation where we will need to continue DFS beyond just the witness's children and so there is a chance that DFS could rule out all other leaf witnesses under the outgoing edge from the candidate, meaning that there is a CHANCE (not guaranteed if there are more outgoing edges unexplored) that this could cause us to query-advance our candidate (once there is provably only one outgoing edge which has any witnesses). This means that our entire query-advancing system and witness search system must be resumable (reactive).

QUERY BIFURCATION DECISION:

Always fork. Queries live only on leaves. When a leaf unfolds, its queries die with it. Each child gets a fresh query for every leftover body goal and a fresh query for every newly added body goal. For a leftover goal we copy the interned pud_rule_id*s (cursor, current witnesses, edge roots that bound those searches) from the parent query — that part is O(1), since the candidate set size is bounded by the number of axioms. We do not inherit the parent’s bind-map recordings. The child’s query is a new search nested in the child’s om_interval, so every ancestor added_unification on the path to a copied witness must be applied again under that interval to see whether the witness still unifies. Copying a query is therefore O(depth) per leftover body goal (direct path replay, not a search of the rest of the DB). If the old witnesses still match, the query suspends there; if specialization killed them, candidate/witness search resumes from those ids. New body goals start candidate search from scratch. No shared query objects, no =@= inherit, no pointer-sharing, no user sets. Search and apply use the same environment: the leaf. We considered inheriting the search object when a leftover goal’s shape did not change, to avoid the path replay; even a cheap shape test still leaves you with overlay/ownership questions, and a rebase is mandatory whenever the shape did change. For now the extra machinery is not worth it.


QUERY RESUMING:

First a note: A candidate can have 2 witnesses (1 down 2 of the outgoing edges) at which we prove that it is a choice point, OR a candidate can actually be ITS OWN witness (in the case that it is a leaf node, and we advanced the query all the way down to it). Maybe we can call these two cases: choice-point or self-witness. In the choice-point candidate case, we expect to have at any point in time, 2 stacks of node ids for resumable DFS. When doing DFS from a given stack, we try to descend further first, and if not possible, we ascend (remembering what the previous child node was before popping from the stack) and then descend down the next child in id-sort-order (children should probably be stored in a map, not unordered_map from the parent).

Also please note: we have a few conflated concepts here. We have "witness search", which is the process for searching for a witness UNDER A SPECIFIC OUTGOING EDGE OF THE CURRENT CANDIDATE. If witness search comes back failed, then we move onto the next outgoing edge in id-sort-order. But remember that when we "resume" a query, we really resume just from a specific witness. This is going to be the witness which was just unfolded. Then, there is the larger concept of query advancing. I think we might refer to the query advancing algorithm as just "candidate search" since that's really what we are doing. OR we could call it "choice point search". But the problem there is that we could fail to find a choice point and still find a valid candidate in the self-witness case, invalidating that name. so "candidate search" is the right word.

NOTES ON VOCABULARY: A "witness" is a LEAF RULE that a query can unify with the head of. If there is an intermediary rule (non-leaf) that matches the same criterion, it is NOT a witness due to it being a non-leaf. A "candidate" is THE MOST SPECIALIZED rule which we can advance a given query to.

So really, when we "resume" witness search due to a witness being invalidated (made non-leaf), we also have the potential for that witness search to fail to find a witness (which again, is under just one of the outgoing edges of the prospective candidate). So at that point, we would want to start searching for a witness under a different, unexplored outgoing edge under the prospective candidate to determine if it is a choice point or not. This means that when a witness is invalidated, we sort of need to resume CANDIDATE SEARCH, not just witness search... not sure what that really means but yeah. Not sure if that will actually boil away when turning these ideas into code, which I have a feeling it may.

In fact, maybe what we do is this. We consider the reactive system to behave in a multilayered fashion. The bottom level of the reaction is when a witness is invalidated, we resume witness search (scanning for a new replacement witness). IF we cannot find a replacement witness, we consider this to be ANOTHER reactive update which makes a call to the prospective candidate which owned that witness to attempt to find a replacement edge which has witnesses. Due to the fact that we already have 2 algo names, we can refer to the second reaction as "candidate invalidation". So two events in our system are: "witness invalidation" and "candidate invalidation", following after "witness search" and "candidate search".

witness search is resumable, and candidate search is resumable. witness invalidation triggers witness search. candidate invalidation triggers candidate search. NOTE: candidates can be re-validated if they switch to a new outgoing edge which it turns out has another witness under it. At that point it is provably a valid choice point once again. Or another thing that could happen is that if we are unable to find another validating witness for the candidate, then we advance down the outgoing edge which DOES still have a valid witness. And resume candidate search there. We could eventually find another choice point OR a self-witnessing candidate.







QUESTIONS:

IS THERE A "QUERY TREE?": No. each query stores a linear container of C (C <= # axioms) entries, where each entry is a candidate. A candiate stores just some cursors describing what the candidate is in the tree, and what its witnesses are in the tree (if it is NOT a self-witness, otherwise the cursor to the candidate itself serves as the witness path).

HOW MANY TREES ARE THERE?: One. The PUD is the only tree in this system that has to be managed manually. There may be maps and things which are abstracted B-trees but the only manual trees are the PUD.

HOW ARE THE `om_interval`s accessed?: Given a pud node id, there will be several lookup maps which return to you the om_interval for that node, in a specific context. The standard (root) context has an om_interval for each node, but then when querying into the tree, each node also has a totally different om_interval pertaining to that query. We likely will have a storage infrastructure specifically allowing quick lookup of an om_interval given a query root (source pud_node_id* of the rule who owns the body goal where the query is attached) and a second pud_node_id* for the target node. This should be used when doing witness search, since we will know the id of each witness as we go and thus can quickly recover what the om_interval is, as well as recover the bindings for that environment.
